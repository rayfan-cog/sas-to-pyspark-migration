## Log review

Full log: `sas_run.log` (5 ERRORs, 3 WARNINGs), sanitized as described under Licensing.

All 5 ERRORs occur in 05_logistic_regression.sas and are downstream of the exported
datasets, which are built from WORK.HOME_EQUITY / _FINAL / _RISK in programs 01-04.
Every PROC EXPORT in 99 and 98 completed; the log records each written file.
Root cause is a real defect in the checked-in SAS code:

```
NOTE: The data set WORK.MODEL_SPLIT has 2717 observations and 33 variables.
NOTE: Variable selected is uninitialized.
NOTE: The data set WORK.TRAIN has 0 observations and 34 variables.
NOTE: The data set WORK.VALID has 2717 observations and 34 variables.
```

`PROC SURVEYSELECT ... method=srs samprate=0.7` (no `OUTALL`) writes only the *selected*
rows and does not create a `Selected` variable, so `if selected = 1 then output work.train;`
routes every row to VALID and leaves TRAIN empty. The cascade:

```
ERROR: The file WORK.LOGIT_MODEL does not exist or it is not a valid item store.
ERROR: File WORK.VALID_SCORED.DATA does not exist.
ERROR: Variable BAD not found.
ERROR: File WORK.ASSOCIATION_STATS.DATA does not exist.
ERROR: Variable BAD not found.
```

Fix (for a future run of program 05): add `outall` to `PROC SURVEYSELECT`.
Note that with `outall` SAS also creates the flag as `Selected`; the DATA step's
`selected = 1` comparison then works.

Warnings, all benign / expected:
- `WARNING: Statement terminated early due to OUTOBS=10 option.` - intentional, `proc sql outobs=10` in 03.
- `WARNING: The data set WORK.VALID_SCORED may be incomplete.` - consequence of the TRAIN defect above.
- `WARNING: Output 'Association' was not created.` - same cause (PROC LOGISTIC ran on VALID via ROC only).

No invalid-numeric-data or uninitialized-variable notes in PROC IMPORT; the import read
5,960 of 5,960 rows cleanly.

## Precision caveat

`99_export_golden.sas` exports `means_by_outcome` with the SAS variable formats inherited
from the source columns (DOLLAR / F8.1), so its output contains rounded and comma-formatted
values such as `"$16,622"` and `40.5`. That output is committed verbatim as
`means_by_outcome_formatted.csv`.

`means_by_outcome.csv` is the same WORK.MEANS_BY_OUTCOME dataset from the same session
re-exported after `format _numeric_;` (formats stripped), and is what the parity tests
compare against:

```
Default,1,997,997,350,16621.965898,40.52080847,10944.471425,17.978908725
Paid,1,4340,4340,3903,19000.714286,33.734581815,11019.700641,6.5059836869
```

Consider adding `format _numeric_;` to the exporter so the committed golden file is
comparison-grade.

## Divergence this run surfaced

The fixture row `CITY = "new york-city"` is `New York-City` in the SAS output: PROPCASE
capitalises after a hyphen, while Spark's `initcap` breaks on whitespace only and yields
`New York-city`. `pyspark/02_data_cleaning.py` uses `initcap` and therefore diverges on
the 20 `winston-salem` rows in the production data too. `tests/parity/pipeline.py`
implements PROPCASE semantics; the migration script has not been changed here.
